# 决策记录

> 记录本项目已做的技术决策，以及**尚未决定**的问题。每条决策都写明理由与被否决的方案，避免后来者重复讨论。

状态标记：**已决定** · **待决** · **建议**（有推荐但未拍板）

---

## D-001 协议选用 OneBot v11 · 已决定

**决策**：以 OneBot v11 作为唯一对外通信契约。

**理由**：

- 生态成熟度最高。v12 规范更新，但协议端、SDK、周边工具的支持远不及 v11。
- 标准化带来解耦收益：协议端被隔离在接入层之后，替换成本低。

**否决的方案**：直接对接 SnowLuma 私有接口 —— 会被单一实现锁定，且其内部接口不保证稳定。

---

## D-002 协议端选用 SnowLuma · 已决定

**决策**：以 SnowLuma 作为默认、首选的协议端。

**理由**：

- 原生输出 OneBot v11 动作与事件，与 D-001 直接吻合，无需中间转换。
- 提供 WebUI、多账号、WebSocket / HTTP 多种接入方式。
- 官方提供 Linux 启动脚本与完整发行包。

**重要约束**：SnowLuma 使用**源码可见非商业许可**，不是 OSI 开源许可。本项目不内嵌、不分发它，仅通过网络协议调用。**更换本项目的许可证不会改变 SnowLuma 的约束。**

**否决的方案**：内嵌协议端 —— 违反进程隔离原则，且会引入其许可与二进制分发问题。

---

## D-003 首选正向 WebSocket · 已决定

**决策**：v0.1.0 优先实现正向 WebSocket（本项目主动连接 SnowLuma）。

**理由**：

- 连接方向在本项目侧，重连、退避、健康检查逻辑可完全自控。
- 部署更简单：无需开放入站端口，适合云主机与内网环境。
- 反向 WebSocket 作为备选保留，其价值场景是**本项目位于 NAT 之后、协议端在公网**。

---

## D-004 进程隔离 · 已决定

**决策**：协议端与本项目为两个独立进程，不做进程内嵌。

**理由**：

- 协议端崩溃不影响本项目状态管理。
- 本项目重启不需要重新扫码登录 QQ。
- 两者的更新、升级、回滚互相独立。

**代价**：多一个需要部署与运维的进程。这是有意接受的成本。

---

## D-005 实现语言 · 已决定：Python

**决策**：使用 **Python** 实现。

**这是本项目的关键决策。** 它决定后续所有代码的形态，因此把完整推理留在这里。

### 决策依据

第一版分析（见本文档修订历史）推荐 Go，理由是部署友好与资源占用。**该推荐已被推翻**，原因有两层：

**第一层：Go 的主要优势经过实测并不成立。**

曾在 Linux 服务器上实测 Python 常驻守护进程（仅加载 `asyncio` / `json` / `sqlite3` / `ssl` / `logging` / `signal`，即本项目所需的最小集）：

| 指标 | 实测值 |
| --- | --- |
| 工作集（Working Set） | **22.8 MB** |
| 私有内存（Private Bytes） | **15.3 MB** |

「Python 内存占用偏高、与 512 MB 目标冲突」这一说法**缺乏实测支撑**。Go 在资源占用上的优势远小于原先估计，而 README 中的 1 核 512 MB 目标对 Python 依然宽松。

**第二层，也是决定性的：项目的可维护性。**

本项目是单人维护的个人项目。维护者明确表示**能读懂 Python，读不懂 Go**。

这意味着若采用 Go：

- 维护者无法独立阅读、调试、修改自己仓库的代码
- 任何功能增补、问题排查都要依赖外部帮助
- 项目实质上脱离了维护者的控制，长期必然停滞

而若采用 Python：

- 维护者能独立维护，项目可持续演进
- 贡献者基数更大，issue 能被处理
- 代价是接受 Python 在性能与部署上的劣势

**结论**：一个理论上更优但维护者看不懂的实现，其长期价值低于一个稍弱但维护者能持续改进的实现。**可维护性优先于性能指标。**

### 本项目对 Python 的适配性

| 需求 | Python 的适配 |
| --- | --- |
| 事件驱动并发 | `asyncio` 成熟，天然适合 WebSocket 长连接与事件分发 |
| OneBot v11 对接 | 有多个成熟实现（`nonebot2` 生态、`aiocqhttp`、`websockets` + 自实现）可供参考或复用 |
| 会话存储 | `sqlite3` 为标准库，无需外部依赖，契合单机部署 |
| 插件系统 | **同等条件下最优**——插件可用 Python 编写，与主程序同语言，无需引入跨语言边界 |
| 部署 | `venv` + systemd unit，自托管场景下足够简单 |
| 资源占用 | 实测 22.8 MB 工作集，符合设计目标 |

### 接受的代价

以下为**已知**并**有意接受**的成本，不掩饰：

1. **单二进制打包困难。** Go 的 `go build` 产出单个静态二进制，Python 需要 PyInstaller / Nuitka 等工具，产物体积大（数十 MB）、启动慢，且对部分 C 扩展支持不佳。**应对**：v0.1.0 采用 `venv` + systemd 部署，暂不做单文件打包；若后续确实需要，再评估 Nuitka。README 中「预编译程序包」的形态需相应调整。

2. **纯 CPU 运算性能较低。** 对按消息计费的机器人负载而言不构成瓶颈，但若将来出现高频消息或本地模型推理场景，需要重新评估。

3. **GIL 限制。** 单进程下 CPU 密集型任务难以并行。**应对**：本项目为 I/O 密集型（网络收发 + 数据库读写），`asyncio` 已足够；如遇瓶颈可拆分子进程。

4. **依赖管理需自律。** 依赖数量失控会同时放大部署复杂度和内存占用。**应对**：优先使用标准库；新增依赖需在评审中说明必要性。

### 被否决的方案

- **Go**：部署与资源占用最优，但维护者无法独立维护——见上文「第二层」。
- **TypeScript**：唯一优势是与 SnowLuma 同栈；但按 D-001 的协议端解耦原则不应依赖其专属 SDK，且部署需 Node 运行时。
- **Rust**：对一人-paced 消息量，性能收益无法抵消开发与维护成本。

### 插件语言

Python 作为主语言确立后，**插件同样使用 Python**——同语言使插件作者无额外学习成本，且无需引入跨语言接口层。

方案 B（子进程插件，任意语言，JSON-RPC over stdio）仍作为**未来扩展**保留：若出现「必须用其他语言编写插件」的真实需求，可在不改动核心的前提下增加该通道。**当前不实现。**

## D-006 插件权限声明 · 建议

**倾向**：插件在清单文件中声明所需订阅的事件类型与所需权限，核心层只投递其声明的事件。

**理由**：最小权限原则；同时避免插件被未订阅事件的海量流量淹没。

**未决**：权限模型如何细分（能否发送消息、能否读取群成员列表、能否访问网络）尚未设计。

## D-007 会话键粒度 · 待决

**倾向**：私聊 `private:{user_id}`、群聊 `group:{group_id}` 为默认；群内按用户隔离的 `group:{group_id}:user:{user_id}` 是否默认开启，还是交由插件声明。

**权衡**：细粒度键上下文更准确，但存储量与模型调用成本显著上升。

## D-008 内置管理面板 · 待决

**问题**：是否提供内置的轻量 Web 管理面板，还是完全依赖配置文件。
